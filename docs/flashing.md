# Flashing firmware

**Every board is flashed over SWD.** There is no bootloader on any of them: the
DB-40 and the custom PCB never had one, and the XIAO's factory Adafruit UF2
bootloader was erased on 2026-09-19 (§ [Why UF2 is gone](#why-uf2-is-gone)).

All boards therefore share one flash layout — application at `0x0`, the seq
checkpoint in the top two pages:

```
0x00000000 - 0x000FDFFF   application            (1016 KiB)
0x000FE000 - 0x000FFFFF   seq checkpoint storage (8 KiB)
0x10001080 - 0x100010A3   UICR provisioning record (36 B, outside the image)
```

A board Cargo feature now selects pins, the battery ADC input and the divider
ratio — **not** a memory map. `memory.x` is generated by
`firmware/board/build.rs`, where every board inherits one shared layout.

⚠️ Because that is all a board feature still selects, a **wiring** is a board:

| Feature | Setup |
|---|---|
| `board-db40` | Raytac MDBT50Q-DB-40 eval board |
| `board-xiao-expansion` | XIAO on the Seeed expansion board — SHT45 on `P0.04`/`P0.05`, permanently powered (development) |
| `board-xiao-breadboard` | XIAO breadboarded — SHT45 on `P1.14`/`P1.13`, rail gated on `P1.15` (alkaline soak node) |

The two XIAO entries are the same silicon. Flashing one where the other belongs
is no longer a brick — every image links at `0x0` — but it drives the wrong pins,
so the sensor reads nothing and only `battery_mv` arrives.

## Development loop

`firmware/.cargo/config.toml` wires `runner` to `probe-rs run --chip
nRF52840_xxAA`, so from inside a firmware crate:

```bash
cargo run --release --no-default-features --features board-xiao-expansion
```

flashes and streams defmt-RTT logs. VSCode's `.vscode/launch.json` carries the
equivalent launch configs, with breakpoints and the Debug Console.

⚠️ **Neither firmware crate has a default board feature.** Every build, check
and clippy invocation must name exactly one, or `board/build.rs` fails with *no
board feature selected*. Cargo features are additive, so pass
`--no-default-features` alongside the one you want.

## Deploying a provisioned sensor

`cargo run` is the edit loop. To put a release artifact on a board that is going
into service, use the provisioning tool instead — it flashes from the artifact
store, guards the image against the board, and keeps the key and the seq counter
straight:

```bash
homescope-provision provision kitchen --firmware sensor-db40   # new board
homescope-provision rotate --firmware sensor-db40              # re-key + reflash
homescope-provision flash --firmware sensor-db40               # firmware only
```

An ordinary flash **does not touch UICR**: `probe-rs` erases only the sectors it
writes, so the device keeps its key and needs no re-provisioning. See
[docs/design/provisioning.md](design/provisioning.md).

## Migrating a XIAO that still has the bootloader

A XIAO flashed before 2026-09-19 runs an application at `0x27000` and keeps its
seq counter at `0x000F2000`. The new layout puts the application at `0x0` and
the counter at `0x000FE000`.

⚠️ **Reflashing alone would be a nonce-reuse bug.** UICR survives a flash, so the
device keeps its key — but the new firmware looks for the counter at an address
that has never been written, finds it blank, and restarts from zero. The same
key with a restarted counter reuses AEAD nonces, which for ChaCha20-Poly1305 is
a break rather than a degradation (see `sensor/src/seq_counter.rs`).

So the migration erases everything and mints a **new** key:

```bash
# 1. Wipe MBR, SoftDevice, bootloader, application, old storage and UICR.
probe-rs erase --chip nRF52840_xxAA

# 2. Re-key and flash in one operation. UICR now reads Blank, which `rotate`
#    accepts — it is the post-chip-erase recovery path — and a fresh key makes
#    the restarted counter safe.
homescope-provision rotate --firmware sensor-xiao-expansion
```

⚠️ **Do not half-migrate.** Flashing at `0x0` without erasing leaves the
bootloader alive at `0x000F4000`, still enterable by double-tapping RESET and
pointing at a stale application — and the new storage region lands on the
bootloader's own MBR-params and settings pages. Erase fully or not at all.

## Why UF2 is gone

The key lives in UICR, and **UF2 cannot write UICR**. So the bootloader could
never finish a provisioning run; it produced a board one SWD visit short of
working, from a flow that needed physical access to the RESET button anyway.

Keeping it cost more than it returned:

- 156 KiB of flash to an MBR and a SoftDevice the firmware never starts (it
  uses `nrf-sdc`), and 128 KiB of RAM reserved for that SoftDevice — which is
  why the receiver could not be built for the XIAO at all.
- A second memory map, a second linker script and a second `app_start`, for a
  board that is retired from RF duty and used as a bench mule.
- ⚠️ A broken recovery path: `ERASEALL` is the only way back into an
  APPROTECT-locked chip, and it wipes the MBR. Flashing a `0x27000` image
  afterwards left `0x0` erased, so the core read `0xFFFFFFFF` as its initial SP
  and reset vector. The board looked dead. That trap is gone now that every
  image links at `0x0`.

Restoring the bootloader is possible — flash the Adafruit hex over SWD — but it
is a probe-only door, so keep a copy if you want it.

**OTA is now an explicit decision, not an inheritance.** The old roadmap
expected BLE DFU through the Adafruit bootloader, and assumed the custom PCB
would carry a ported build of it. That option is still open, but it has to be
chosen and flashed deliberately — and it would only ever cover firmware
*updates*, never provisioning, since DFU cannot write UICR either.
